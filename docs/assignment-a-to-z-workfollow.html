3. Architecture: What Was Used and Why

Decision Where It Is Implemented Why This Was Chosen When Another Option Is Better
Laravel modular monolith app/Domains/*, config/domains.php, App\Providers\DomainServiceProvider, routes/domains/*.php The assignment is one Laravel app with many business domains. Modular monolith keeps one deploy and one database while avoiding one huge controller/model folder. Use microservices only when independent teams, separate scaling, and service ownership justify distributed complexity.
Service layer for business logic CheckoutService, PricingService, InventoryService, WorkflowEngineService, CampaignDispatchService, SupportTicketService Controllers stay thin and business rules remain testable. For very small CRUD apps, direct Eloquent from controllers can be acceptable, but not for this assignment's linked workflows.
Event/listener workflow EventServiceProvider, OrderPlaced, RfqCreated, SupportTicketCreated, workflow listeners Order, RFQ, ticket, and social events can trigger automation without hardcoding every side effect in the request controller. Use simple synchronous service calls for tiny flows where no cross-module automation exists.
React + Inertia resources/js/app.jsx, resources/js/Pages/**/*.jsx, resources/views/app.blade.php Gives dynamic dashboard/workspace UI without building a separate SPA API authentication layer. Use Blade-only for mostly static admin forms. Use a separate SPA only when frontend/backend teams and API contracts are independent.
Tailwind CSS tailwind.config.js, resources/css/app.css, React components Creates a polished custom business UI and avoids Bootstrap-looking generic admin screens. Use Bootstrap if speed and standard components matter more than custom product UI.
Provider adapters and mocks MockEmailProvider, MockSmsProvider, MockFacebookPublisher, MockInstagramPublisher, LiveFacebookPublisher The assignment asks for SMS/social/email, but real paid credentials may not be available. Adapter design proves the flow and keeps live integration replaceable. Use direct SDK calls only for small internal scripts, not a platform that needs testable integrations.

9. Remaining Notes and Honest Caveats

  • Provider credentials Email/SMS/social real delivery depends on .env credentials. Mock providers are correct for demo proof, not final live customer delivery.
  • Social live mode Facebook live publisher exists; Instagram is intentionally mock unless a real Instagram provider is configured later.
  • Queue mode QUEUE_CONNECTION=sync is fine for local/demo. Production should use database or Redis worker with Supervisor/systemd.
  • Docs link The operations runbook is available at docs/operations.html, and README.md points to that actual file.
  • Source-doc gap list The fresh source-document comparison is in docs/requirement-proof-guide.html. Previously flagged RFQ/API/repository/DTO/envelope gaps are now implemented; the remaining recommendations are optional production hardening items.
  • Original PDF scope The PDF marks chatbot API and Instagram API as optional/mockable. This implementation covers chatbot API and uses mockable social providers where live credentials are unavailable.
  • Not in PDF Returns/refunds, shipping carrier integration, tax rules, multi-company tenancy, CSV import/export, and advanced analytics are not explicit PDF requirements. Add them only if the evaluator asks for enterprise extras.
